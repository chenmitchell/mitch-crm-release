# 設定說明

這套系統的設計方向是:裝好之後不改一行程式就能用。前台看到的業務用語清單
(客戶階段、場所類型、必拍照片、互動管道)都有對應的後台設定頁,改完立即生效。

把關的門檻還沒有走到這一步,目前多半是程式常數或環境變數,哪一項在哪裡見第三節 3.1。

這份文件說明首次啟動精靈每一步在設什麼、裝完之後要在哪裡改,以及哪些東西目前還沒有。

---

## 一、精靈與後台是同一份設定

首次啟動精靈不是另一套東西。它只是把後台的設定頁按順序走一遍,寫進去的是同一組設定表。

所以有兩件事可以放心:

- 精靈裡填錯的東西,之後在後台改就好,不用重裝
- 精靈裡每一步都可以先跳過,跳過就用預設值,之後再回頭設

精靈問得比較多,是為了讓人裝完就能真的開始用,不是為了刁難。

### 但精靈本身要當成一個要盡快關上的視窗

精靈的端點沒有登入守衛。這不是疏忽:還沒有任何帳號的時候,沒有人登得進來,
要求先登入等於誰都裝不起來。把關的條件是「資料庫裡還沒有任何使用者」,
一旦有任何一位使用者,精靈的端點就一律拒絕,不會變成後門。

要注意的是關上之前那段時間:**服務起來到有人完成精靈為止,任何連得到網址的人
都可以走完精靈、把管理員設成自己的。** 所以部署完成後請立刻把精靈走完,
或是乾脆用環境變數先把管理員建好(見下面第二步),讓精靈自始不出現。
對公網開放的部署尤其要注意。完整說明見 [`SECURITY.md`](../SECURITY.md)。

## 二、精靈的九個步驟

精靈的順序就是 `apps/frontend/src/app/setup/page.tsx` 裡的九步,底下依序說明。

畫面上的步驟列寫的是「共 10 步」:第十步是「完成」,只有一個確認畫面,沒有東西要填,
所以這裡不另外列。

### 第一步:組織名稱

四格文字:組織全名(頁尾的版權列)、組織顯示名(比較短的稱呼,站頭副標用)、
產品名稱(這套系統在畫面上叫什麼)、站頭商標文字(留空就用產品名稱)。

沒有 Logo 圖檔上傳,商標是一段文字。對外聯絡電話與收件地址不在精靈裡,
裝完之後在後台補。組織全名會印在照片浮水印的中央淡蓋上,所以填的是對外要顯示的名稱。

之後在哪裡改:後台系統設定的「組織與品牌」頁籤。

### 第二步:管理員帳號

信箱、姓名、密碼(至少 12 個字元)。這個帳號是系統管理員。

`SEED_ADMIN_PASSWORD` 留空時不會自動建立任何帳號,也不會有初始密碼可抄,
管理員就是在這一步當場設定的。密碼由你自己輸入,不會出現在任何容器的 log 裡。

反過來,`.env` 裡同時填了 `SEED_ADMIN_EMAIL` 與 `SEED_ADMIN_PASSWORD` 的話,
管理員在服務起來時就建好了,首次登入強制改密碼,精靈不會出現。兩者只能擇一:
資料庫裡一旦有帳號,精靈就關閉。對公網部署建議走這一條,理由見上一節。

之後在哪裡改:後台的使用者管理。

### 第三步:時區與地區

兩格下拉:時區(IANA 字串)與地區語言。

日期計算已經接上這一格:打卡的日期、日報的日期界線、拜訪計畫的「今天」、
統計的日期分組,後端都從 `OrgTimeService` 讀組織時區;照片浮水印的時間、
畫面浮水印的時鐘、首頁「今日三件事」的日期,前端也照同一格算,不再寫死 UTC+8。

時區只影響日期與時間怎麼分組、怎麼顯示。已經存下來的時間戳記本身是 UTC,改時區不會動到舊資料。

之後在哪裡改:後台系統設定的「時區與地區」頁籤。

### 第四步:部門與主管

一列一個部門:部門名稱、主管姓名、主管 Email。主管 Email 對不到已建立的帳號時,
系統只建部門、不指派主管。

精靈這一步只建得出平的一層。要建成一棵樹,裝完之後到後台的「組織部門」頁籤,
每個部門在那裡才選得了上層部門:

```
總公司
├─ 北區
│  ├─ 一課
│  └─ 二課
└─ 中區
   └─ 三課
```

部門樹決定主管看得到誰。訪查主管看得到兩群人名下的客戶:所屬主管指向自己的人
(可遞迴),以及自己所屬部門子樹裡的成員。用子樹而不是直屬下級,是因為區經理
要看得到底下三個課的所有人。

一位使用者只歸屬一個部門,所以「一位主管同時管兩個平行部門」目前只能靠
把那些人的所屬主管指向他來達成,不能給他掛兩個部門。

之後在哪裡改:後台系統設定的「組織部門」頁籤,人員的歸屬在使用者管理。

### 第五步:客戶階段

看板上會有哪幾欄。沒有範本可以挑,精靈帶出來的是出廠那一組,直接在上面改:

名單、已接觸、已拜訪、報價中、有意願、已成交、無效/放棄

每個階段有代碼、名稱、顏色、排序,以及三個開關:是不是終止階段(成交或放棄這類,
不再算進行中,逾期追蹤與待辦都不看它)、要不要出現在看板欄位、要不要出現在表單下拉。
沒有「初始階段」或「失敗結案」這兩種標記。

`converted` 與 `dropped` 是產品保留的兩個代碼,名稱、顏色、排序都可以改,不能刪:
標記成交與查重合併會寫進這兩個值。

刪階段要處理既有資料。底下還有客戶的階段刪不掉,系統會擋下來並告訴你還有幾位客戶
停在那一階,要自己先把那些客戶改到別的階段,或者把階段改成停用。停用的階段不再出現
在看板,既有資料保留。這是必要的把關,不然刪一個階段就會讓一批客戶變成孤兒。

刪掉之後就是刪掉了,重啟不會自己回來。系統每次開機都會補一次出廠設定
(這是為了讓日後新增的出廠值也進得去既有的安裝),但刪除會另外記一筆
「這個代碼是被刻意刪掉的」,補的時候會跳過它。同一個代碼自己再加回來的話
那筆記錄就會清掉,行為回到出廠狀態。這一條對客戶階段、照片種類、互動管道、
場所類型、商業分類五份主檔都成立。

之後在哪裡改:後台系統設定的「客戶階段」頁籤。

### 第六步:照片存證檢查表

這是這套系統的核心設定。

照片種類與場所類型是兩份主檔,照片種類上面掛「這一種在哪些場所類型是必拍」。
出廠值只有兩種場所類型與七種照片種類:

| 場所類型 | 出廠必拍的照片種類 |
|---|---|
| 實體店面 | 門牌、外觀、內部、物品 |
| 辦公室 | 門牌、外觀、招牌、環境 |

另外有一項「其他」,不分場所、不必拍。標籤刻意用通用詞,工地、農地、住家這些
自己在後台加,加場所類型與加照片種類都不必改程式。

每一項照片種類有:代碼、顯示名稱、是否必拍、適用哪些場所類型(留空 = 所有場所)。
沒有說明文字欄位,也沒有範例圖。

之後在哪裡改:後台系統設定的「照片存證檢查表」與「場所類型」兩個頁籤。改動只影響
之後的檢查,已經標記成交的不會被回頭要求補拍。

必拍沒到齊時一律擋住標記成交,這是寫死的行為,沒有「只警告」的選項。

一種場所沒有任何必拍項目時,系統會擋住成交並要人先去設定。原因是「沒有必拍項目」
本身有兩種意思:管理員還沒設,或這種場所本來就不用拍。分不出來就只能一律擋 ——
放行的話,新增一個場所類型而忘了設必拍,那個類型的客戶零張照片就標記得了成交,
而畫面上不會有任何提示。

真的有不用拍照的場所(例如純線上客戶)時,到後台「照片存證檢查表」頁籤的
「每一種場所目前的狀態」把那一種勾成**不需照片存證**。勾了就放行,一張都不要求。
同一區塊會把每一種場所的狀態直接寫成文字:必拍幾項、不需照片存證、或尚未設定會擋成交。
這一段只在後台,精靈裡沒有 —— 豁免是裝好之後才會遇到的例外。

### 第七步:地圖與地理編碼

- 拜訪地圖的預設中心(緯度、經度)與預設縮放層級。地圖打開時鏡頭就停在這裡
- 地理編碼服務:只有「OpenStreetMap Nominatim」與「不啟用」兩個選項。沒有商業地圖服務的選項,也沒有 API 金鑰欄位。
  選「不啟用」之後,補齊座標、背景補座標與反查路名三條對外路徑一律不發出請求,座標全部人工填
- 限制國家:逗號分隔的兩碼國碼(ISO 3166-1 alpha-2),例如 `tw`,或 `jp,kr`。
  **留空就是不限制國家**,而那是出廠值

限制國家這一格填了之後,查不到的地址就只會是那幾國裡查不到。裝在單一國家的組織填上
自己的國碼可以少掉一些同名誤中;跨國營運的就留空。填進去的內容會逐段檢查,
不是兩個英文字母的段落一律丟掉,所以貼錯東西不會變成送出去的查詢參數。

自架 Nominatim 的位址、送出去的 User-Agent 產品名、以及公用端點要求的聯絡信箱,
這三格不在精靈裡,在後台同名頁籤設定。聯絡信箱留空時會退回環境變數
`NOMINATIM_EMAIL`,兩邊都沒有才用 placeholder,請求可能被擋。

之後在哪裡改:後台系統設定的「地圖與地理編碼」頁籤。

### 第八步:外部查詢帶入

要不要用外部服務把識別碼換成名稱、地址、電話。五個欄位的意義、設定範例與安全限制
見下面的 3.4,精靈這一步與後台同名頁籤改的是同一組設定。

之後在哪裡改:後台系統設定的「外部查詢帶入」頁籤。

### 第九步:外觀

配色方案(藍綠或赤陶)、側欄底色(深或淺)、預設日夜模式(跟隨作業系統、淺色、深色),
以及後台四個功能區各自的識別色。

識別色只能從固定幾組挑,不能自由填色碼:每一組的對比在淺色與深色模式都量過,
自由填很容易讓文字掉出無障礙標準。個別使用者仍可自己切換日夜模式,那個存在瀏覽器本機。

之後在哪裡改:後台系統設定的「外觀」頁籤。

## 三、精靈以外的設定

後台系統設定共十二個頁籤:組織與品牌、時區與地區、客戶階段、照片存證檢查表、
互動管道、場所類型、商業分類、地圖與地理編碼、外部查詢帶入、外觀、組織部門、存取與帳號。
其中四個是精靈裡沒有的。

原本還有一個「通知」頁籤,四格分別是瀏覽器通知開關、每日提醒時間、寄信開關與寄件人位址。
那四格全 repo 沒有任何讀取端:後端沒有排程器也沒有寄信實作,前端沒有推播註冊,
改它們不會改變系統的任何行為。讓人設一個沒有效果的東西比不給設更糟,所以精靈與後台
都已經把它拿掉。設定鍵本身保留,舊資料庫裡存過的值讀得出來也不會出錯。

實務上的影響:邀請連結一律要自己複製網址,用通訊軟體或既有管道傳給對方;
密碼重設同樣由管理員在後台的使用者管理直接處理,不會有重設信。
真的要做通知時,得連同排程器與寄信元件一起補,再把設定頁加回來。

### 3.1 把關規則:哪些改得到、哪些改不到

這一節列的門檻不是設定值,現階段全部在程式常數或環境變數裡。後台沒有這幾格,
文件寫出來是為了讓人知道實際的判定標準,不是叫人去設定頁找。

下面三張表是完整清單:凡是會讓使用者看到「被擋下來」訊息的門檻都在裡面。
沒列進來的行為就是沒有門檻。

**現場判定**

| 規則 | 現值 | 在哪裡 |
|---|---|---|
| 打卡距離門檻 | 1500 公尺 | 程式常數 `SUSPICIOUS_DISTANCE_M`(`apps/backend/src/crm/checkin/checkin-rules.ts`) |
| 定位精度門檻 | 300 公尺 | 同上,`SUSPICIOUS_ACCURACY_M` |
| 裝置與伺服器時間差 | 5 分鐘 | 同上,`SUSPICIOUS_CLOCK_SKEW_MS` |
| 兩次打卡之間的移動速度 | 120 km/h,回看 2 小時 | 同上,`SUSPICIOUS_SPEED_KMH` |
| 地址變更 / 合併的可疑視窗 | 24 小時 | 同上,`ADDRESS_CHANGE_WINDOW_MS` |
| 照片拍攝時間與伺服器時間的容許差 | ±24 小時,超出就拒收 | 同上,`TAKEN_AT_MAX_SKEW_MS` |
| 必拍照片沒到齊 | 一律擋住標記成交 | 寫死的行為,沒有「只警告」的選項 |

客戶沒有座標時,打卡會記一句「客戶尚無座標,未比對距離」,但那**不算可疑**。
以前「建檔不到 24 小時而且還沒有座標」會另外標成可疑,實際效果是每一位新客戶的
第一次到訪都亮紅燈:地理編碼出廠不啟用,新客戶本來就不會有座標,就算啟用了,
編碼是背景排程,剛建好的客戶也還沒編到。整條規則對真的造假沒有鑑別力,
只會讓主管學會忽略紅燈,所以拿掉了。24 小時內【地址變更】或【合併】那兩條留著,
那兩件事是有人在既有客戶上動過手腳才會出現的。

**照片上傳額度**(四層疊在一起,任何一層超過都會被擋,訊息直接寫出上限)

| 規則 | 現值 | 在哪裡 |
|---|---|---|
| 單張照片大小上限 | 600 KB | 程式常數 `PHOTO_MAX_BYTES`(`checkin-rules.ts`) |
| 一次上傳張數上限 | 8 張 | 同上,`PHOTOS_MAX_COUNT` |
| 一次上傳總量上限 | 3 MB | 同上,`PHOTOS_TOTAL_MAX_BYTES` |
| 每位客戶累計張數上限 | 40 張(含歷史所有互動掛的照片) | 同上,`CUSTOMER_PHOTOS_MAX_COUNT` |
| 每位客戶累計總量上限 | 20 MB | 同上,`CUSTOMER_PHOTOS_MAX_BYTES` |
| 每位使用者每日上傳總量上限 | 100 MB(組織時區的日曆日) | 同上,`USER_DAILY_UPLOAD_MAX_BYTES` |

**時效、額度與速率限制**

| 規則 | 現值 | 在哪裡 |
|---|---|---|
| 邀請連結有效時間 | 30 分鐘 | 程式常數 `INVITE_TTL_MINUTES`(`apps/backend/src/invites/invites.service.ts`) |
| 邀請連結每小時上限 | 同一發送人 10 條 | 同上,`INVITE_QUOTA_PER_HOUR` |
| 登入失敗鎖定 | 5 次 / 鎖 30 分鐘 | 環境變數 `LOGIN_MAX_ATTEMPTS`、`LOGIN_LOCKOUT_MINUTES` |
| 登入效期 | 8 小時,過半自動續期 | 環境變數 `JWT_ACCESS_TTL` |
| 日報可補交天數 | 7 天 | 程式常數 `SUBMIT_BACKFILL_DAYS` |
| 「久未聯絡」判定 | 7 天沒有互動 | 前端常數 `HOT_STALE_DAYS`(`components/crm/today-top3.tsx`) |
| 全站每 IP 速率限制 | 每 60 秒 100 次 | 環境變數 `THROTTLE_LIMIT_DEFAULT`、`THROTTLE_TTL_SECONDS` |
| 錯誤記錄保留期 | 30 天 | 環境變數 `ERROR_LOG_RETENTION_DAYS` |
| 稽核記錄保留期 | 730 天(兩年);0 = 永不刪除 | 環境變數 `AUDIT_LOG_RETENTION_DAYS`,只接受 0 或 90 到 3650 |
| 一次查重最多比對 | 10000 筆客戶 | 程式常數 `DUPLICATE_SCAN_LIMIT`(`apps/backend/src/crm/duplicates/crm-duplicates.service.ts`);超過時查重頁用負責人與階段篩選縮小範圍 |
| 登入與改密碼端點 | 每分鐘 10 次 | 環境變數 `THROTTLE_LIMIT_STRICT`(`auth.controller.ts` 的 `@Throttle`) |
| 打卡與補拍上傳端點 | 每分鐘 10 次 | `crm-checkin.controller.ts` 的 `UPLOAD_THROTTLE` |
| 邀請連結檢查端點 | 每分鐘 20 次 | `invites.controller.ts` 的 `CHECK_THROTTLE` |
| 邀請連結接受端點 | 每分鐘 10 次 | 同上,`ACCEPT_THROTTLE` |
| 單一登入設定的連線測試端點 | 每分鐘 6 次 | `entra-admin.controller.ts` 的 `@Throttle`(這支會對外發請求) |

逾期跟進沒有天數門檻:比的是每位客戶自己那一格「下次跟進日」,過了今天就算逾期。

打卡的距離與精度只影響「可疑」標記,不會擋住打卡。照片拍攝時間超出 ±24 小時則是真的拒收。

速率限制是**每 IP** 算的,不是每帳號。同一個辦公室共用對外 IP 時,人多的話上傳端點
那條每分鐘 10 次會提早撞到,要調整就改上面列的常數或環境變數。

### 3.2 互動管道與場所類型

互動管道出廠七項:拜訪、電話、通訊軟體、電子郵件、報價、備註、其他。可以增減、改名、排序。

`visit` 與 `note` 是保留代碼,不能刪:到訪打卡只寫得進 `visit`,系統紀錄(移交、成交、
合併、地址變更)寫的是 `note`。有互動紀錄用過的管道也刪不掉,只能停用。

場所類型出廠兩項:實體店面、辦公室。照片存證檢查表是按場所類型分組的,所以要加一種
新的現場(工地、農地、住家),就從這一頁加起。已經有客戶屬於的場所類型刪不掉。

### 3.3 組織部門與存取

組織部門就是第四步那棵樹,在這裡才選得了上層部門。存取與帳號那一頁是入口,
連到單一登入設定、使用者管理與團隊成員三處。

### 3.4 外部查詢帶入

「輸入一組識別碼,自動帶入名稱、地址、電話」。預設關閉,關閉時那一格就是純手動輸入欄位。

這一組刻意不內建任何一個資料源。各地都有自己的公開登記資料,那個號碼叫什麼、要打哪個網址、回應長什麼樣子全都不一樣,內建任何一個等於把產品綁在一個國家。所以系統只提供一個由設定驅動的殼,資料源由架設的人自己接。

安裝精靈的「外部查詢帶入」那一步,以及後台「系統設定」的同名頁籤,改的是同一組設定。五個欄位:

| 設定 | 預設 | 說明 |
|---|---|---|
| 啟用外部查詢帶入 | 關閉 | 關著時新增客戶頁不會出現「查詢帶入」按鈕,欄位本身留著 |
| 識別碼的名稱 | 公司登記編號 | 這個號碼在當地怎麼稱呼。全站的欄位標籤、提示與錯誤訊息都用這個字 |
| 查詢網址樣板 | 空 | `{q}` 會被使用者輸入的識別碼取代 |
| 回應欄位對應 | 空 | 外部服務回的 JSON 要怎麼對到名稱、地址、電話三格 |
| 識別碼格式 | 空 | 正規表示式,送出前先擋掉明顯打錯的值。留空 = 不檢查 |

「啟用外部查詢帶入」關著的時候,**客戶匯出 CSV 的第一欄標題會退回通用名稱「公司登記編號」**,
不用「識別碼的名稱」那一格填的字。理由是那一格是跟著查詢功能一起設的,填進去的常常是
功能的名字而不是欄位的名字,而匯出檔是會寄出去、會匯進別的系統的東西,不該帶著一個
系統裡已經關掉的功能的名字。匯出檔照樣匯得回來:匯入是按欄位位置解析的,不看標題文字。

#### 一個完整的例子

假設你要接的服務是 `https://registry.example.com/lookup?id=<號碼>`,回的 JSON 長這樣:

```json
{
  "status": "ok",
  "data": {
    "company_name": "範例商行",
    "addr": "某市某區某路 1 號",
    "tel": "02-1234-5678"
  }
}
```

那五格就這樣填:

- 啟用外部查詢帶入:打勾
- 識別碼的名稱:依當地的正式名稱填,例如「商業登記號碼」
- 查詢網址樣板:`https://registry.example.com/lookup?id={q}`
- 回應欄位對應:名稱填 `data.company_name`、地址填 `data.addr`、電話填 `data.tel`
- 識別碼格式:如果當地的號碼固定是八位數字,填 `\d{8}`;不固定就留空

路徑用點分隔,一層一層指下去,陣列用數字當索引,例如 `results.0.name`。對應留空的欄位不會被帶入,已經填好的值也不會被蓋掉。

#### 安全限制

查詢是**伺服器**去打的,不是瀏覽器。所以網址填錯的後果不只是查不到,而是有人可以叫伺服器去打內部網路。系統在存檔那一刻與送出請求之前各擋一次:

- 只接受 https。http 一律拒絕
- 不可以把帳號密碼寫在網址裡
- 不可以指向 localhost、私有網段(10、172.16 到 172.31、192.168)、連結本地(169.254,含雲端 metadata 位址)、單一標籤的內網主機名,以及 `.local`、`.internal` 這類保留名字空間
- 主機名解析出來的位址也要全部是對外位址。用一個公開網域指向內網 IP 一樣會被擋
- 不跟隨轉址。跟隨的話等於讓對方決定我們去打哪裡
- 逾時 8 秒,回應大小上限 64KB
- 上游的狀態碼與錯誤內容不會顯示給使用者,只寫進伺服器記錄。使用者看到的一律是「外部查詢服務目前無法使用,請手動填寫」
- 端點有獨立的速率限制(每分鐘 20 次),避免被當成打上游的轉發器

如果外部服務需要金鑰,把金鑰放在查詢字串裡(例如 `https://registry.example.com/lookup?key=…&id={q}`)。這一格只有系統管理員讀得到,免登入的公開設定端點不會回傳網址樣板與欄位對應,只回「有沒有啟用」「識別碼叫什麼」「格式是什麼」三項。

#### 沒有啟用的時候

識別碼欄位照常存在,只是變成純手填,不會出現「查詢帶入」按鈕與那一行說明。這時候直接打查詢端點會拿到 404,訊息會說明要去哪裡開。


### 3.5 單一登入

選用。不設定就只有帳號密碼登入。設定之後帳號密碼仍然可用,兩種方式並存。
設定入口在「存取與帳號」頁籤裡的「前往單一登入設定」。

**憑證不在後台填。** 那一頁存的是政策 —— 哪些信箱網域可以登入、要不要自動建帳號、
自動建的帳號放哪個部門與哪位主管 —— 找不到填識別碼與密碼的地方是刻意的。
四個憑證值只能從環境變數給:

| 變數 | 從哪裡拿 |
|---|---|
| `ENTRA_TENANT_ID` | Entra 系統管理中心 → 應用程式註冊 → 概觀,「目錄 (租用戶) 識別碼」 |
| `ENTRA_CLIENT_ID` | 同一頁的「應用程式 (用戶端) 識別碼」 |
| `ENTRA_CLIENT_SECRET` | 應用程式註冊 → 憑證及密碼 → 用戶端密碼(建立後只顯示一次) |
| `ENTRA_REDIRECT_URI` | 你自己決定,但要與應用程式註冊裡填的一字不差,結尾不要多斜線 |

Docker Compose 與 Zeabur 兩條路線都已經把這幾個轉發進容器:在 `.env`(或 Zeabur 的
服務變數)填好,重啟 backend 就生效。四個沒有全部填齊時,登入頁不會出現 Microsoft 按鈕 ——
半套設定會讓人按下去之後才失敗,所以乾脆不顯示。

## 四、後台控制前台的原則

這一節是給要改這套系統的人看的,也是 pull request 的驗收標準之一。

**第一條:前台不得出現寫死的業務用語清單。** 階段、場所類型、照片項目、互動管道
已經照這條做完,一律從設定讀。角色顯示名稱還沒有,見下一節。

**第二條:把關規則要盡量做成設定值。** 這一條目前完成度最低:3.1 那張表列的門檻
全部還在程式常數或環境變數裡。新增把關規則時不要再加一條寫死的。

**第三條:新功能如果冒出一個「暫時寫死」的清單,就要同時補上它的設定頁。**
沒有設定頁的清單不准進主線。

第三條最容易破功,所以有自動檢查:CI 會掃前端原始碼,發現寫死的業務語彙清單就紅燈。

這一節寫的是二〇二六年九月當下的狀態,程式還在動,對不上的時候以程式為準。

以下是文件裡看得到、但目前**還沒有**的東西,不要照著找:

- **角色顯示名稱不能改。** 可指派的角色固定三個(系統管理員、訪查主管、訪查人員),
  標籤寫死在前端 `lib/roles.ts`
- **沒有結案原因設定。** 系統沒有這個設定鍵,也沒有這個欄位
- **浮水印沒有設定頁。** 要印哪些欄位、密度、透明度、角度都寫死在程式裡
- **照片只存資料庫。** 沒有物件儲存的實作,也沒有切換的設定
- **沒有通知功能。** 沒有排程器、沒有寄信實作、沒有瀏覽器推播註冊。
  首頁「今日三件事」的提醒是使用者自己按下按鈕、由瀏覽器當場推一次,不是排程來的
- **稽核記錄沒有後台查詢畫面。** `audit_logs` 寫進去的有:單一登入的成功與失敗、
  客戶的刪除與整批刪除、還原、永久刪除,以及每一次資料匯出。要看得直接查資料庫。
  完整清單見 [`SECURITY.md`](../SECURITY.md) 的「目前還沒有的防線」
- **停用帳號、改角色、改密碼都會即時生效**(每次請求回查 users 那一列,
  並比對 `password_changed_at`),但沒有「列出我的登入裝置、逐一登出」這種畫面
