# 安裝與部署

適用對象:要把 Mitch CRM 裝起來的人。不預設任何雲平台,自架與 PaaS 都涵蓋。

---

## 一、系統需求

### 硬體

| 規模 | CPU | 記憶體 | 磁碟 |
|---|---|---|---|
| 試用或小團隊(10 人以下) | 2 核 | 4 GB | 40 GB |
| 一般(50 人以內) | 4 核 | 8 GB | 100 GB |
| 較大(100 人以上) | 4 核以上 | 16 GB | 200 GB 以上 |

磁碟主要吃在照片。照片存在資料庫裡(目前沒有物件儲存的選項),一張壓縮後約 200 KB 到 500 KB。粗估:每人每天 6 張、每月 22 個工作天,50 人一年約 40 GB。量大就要把資料庫那顆磁碟開大一點,或自己定期把舊照片搬出去。

#### 照片存資料庫的容量風險

備份簡單是好處,代價是「寫進去的東西很難拿出來」:照片與客戶資料在同一顆資料庫裡,單張刪除對**已結案**的客戶是擋住的(那是存證,不能事後抽換),所以真正的清理要有人直接連進資料庫做。

系統本身有四層上限擋住單一帳號的寫入量,把最壞情況算成具體數字:

| 層級 | 上限 | 擋掉的情境 |
|---|---|---|
| 每張照片 | 600 KB | 未壓縮的原圖 |
| 每次上傳 | 3 MB(最多 8 張) | 一次塞滿放寬到 5 MB 的 body |
| 每位客戶累計 | 20 MB(最多 40 張) | 同一家客戶被重複灌照片 |
| 每位使用者每日累計 | 100 MB | 同一個帳號一直建新客戶來繞過上一層 |

沒有最後那一層的話,前三層全部是「以客戶為單位」的,而建客戶只吃預設的請求額度(每 IP 每分鐘 100 次)。一個登入帳號可以一直建新客戶、每個各塞 20 MB:上傳端點每 IP 每分鐘 10 次、每次 3 MB,等於每分鐘穩定寫入 30 MB,約 **43 GB/天**,而且沒有盡頭。加上每日 100 MB 的上限之後,同樣的帳號一天最多寫入 0.1 GB,50 人的組織即使全員每天寫滿也是 5 GB/天,落在上面那張規格表的估算範圍內。

要調整上限的部署方改 `apps/backend/src/crm/checkin/checkin-rules.ts` 的 `USER_DAILY_UPLOAD_MAX_BYTES`(以及同一支檔案裡的其他三個常數)。放寬之前先照上面的算式重算一次磁碟。

### 軟體

用 Docker 部署(建議):

- Docker 24 以上
- Docker Compose 2.24 以上。低於這個版本的話,接外部資料庫用的疊加檔會失效,因為它用到 `!reset` 與 `!override` 標籤

不用 Docker 的話:

- Node.js 20.20.2(見 `.nvmrc`,`package.json` 的 engines 接受 `>=20.11.0 <23.0.0`)

  這裡有三個數字,關係是這樣:`engines` 是**下限**,20.11 是 `import.meta.dirname` 開始能用的版本,
  CI 的幾支腳本靠它定位 repo 根目錄;`.nvmrc` 是本機與 CI 實際安裝的版本;
  兩份 Dockerfile 的 `NODE_IMAGE` 是容器裡跑的版本。後兩者刻意寫成同一個版本號,
  改版時三處要一起看,不要只改其中一個。
- pnpm 10 以上
- PostgreSQL 16
- 一台反向代理(nginx、Caddy、Apache 都行)

執行期不需要 LibreOffice、無頭瀏覽器或任何外部轉檔程式。

### 對外連線

| 目的地 | 必要性 | 說明 |
|---|---|---|
| 地理編碼服務 | 建議 | 沒有就無法把地址轉成座標,拜訪地圖只顯示有座標的客戶 |
| 地圖圖磚服務 | 建議 | 沒有就看不到底圖,清單與打卡功能不受影響 |
| 寄信服務 | 不需要 | 目前版本沒有寄信實作,不會連線到任何郵件服務。邀請連結請自己複製後傳給對方 |
| Let's Encrypt | 視情況 | 由內建反向代理自動申請憑證時才需要。用公司自己的憑證就不需要 |
| 容器映像檔來源 | 建置時 | 只在建置階段需要。正式機不能對外的話,先在別的機器建好映像檔再推進內部 registry |
| npm registry | 建置時 | 只在建置階段需要 |
| Prisma 引擎下載 | 建置時 | `prisma generate`(`pnpm type-check` / `pnpm test` / `pnpm build` 都會先跑它)會去 `binaries.prisma.sh` 抓查詢引擎與 schema 引擎的二進位檔,那不是 npm registry。**只放行 registry 的機器會在後端這一段直接失敗**,訊息是 `Failed to fetch the engine file at https://binaries.prisma.sh/... - 403`。離線環境要先把引擎檔放到機器上,再設 `PRISMA_QUERY_ENGINE_LIBRARY`、`PRISMA_SCHEMA_ENGINE_BINARY`、`PRISMA_QUERY_ENGINE_BINARY` 指過去,並加上 `PRISMA_ENGINES_CHECKSUM_IGNORE_MISSING=1`(`turbo.json` 已經把這幾個變數列進 passThroughEnv) |
| Google Fonts | 建置時 | 前端用 `next/font/google` 把 Noto Sans TC 抓下來自架,`next build` 會實際連 `fonts.googleapis.com` 與 `fonts.gstatic.com`。**只放行 npm registry、把這兩個網域擋掉的建置機器會直接在 frontend 這一段建置失敗。** 離線建置在 `.env` 設 `NEXT_FONT_GOOGLE_MOCKED_RESPONSES=/src/scripts/build/next-font-google-mock.cjs`,改用 repo 內附的離線替身,畫面退回系統字型,版面與功能不受影響 |

系統本身不會主動對外傳送任何資料。

## 二、路線 A:Docker Compose 單機

四個容器:PostgreSQL、後端、前端、反向代理。前後端共用一個對外網址,由反向代理依路徑分流,所以不必處理 CORS,cookie 也不會因為跨網域被瀏覽器丟掉。

```bash
git clone https://github.com/chenmitchell/mitch-crm.git
cd mitch-crm
bash scripts/setup.sh
```

`setup.sh` 會產生 `.env`,並自動填入隨機的資料庫密碼與 JWT 金鑰。Windows 上用 `scripts/setup.ps1`。

接著編輯 `.env`,至少確認這幾項:

- `PUBLIC_BASE_URL`:使用者實際會打的網址。這一項填錯,系統不會報錯,但產生的邀請連結會指向錯的地方
- `SEED_ADMIN_EMAIL`:自動建立管理員時要用的信箱。選填,走首次啟動精靈的話留空即可,沒設不影響起站;要用環境變數自動建管理員時才連同 `SEED_ADMIN_PASSWORD` 一起填
- `SITE_ADDRESS`:純 HTTP 試跑就留 `:80`;要讓內建反向代理自動申請憑證,就填網域名稱,同時把 `APP_PORT` 設 80、`APP_HTTPS_PORT` 設 443,而且該網域的 DNS 要已經指到這台機器
- `COOKIE_SECURE`:走 https 設 `true`,純 http 一定要 `false`

然後起站:

```bash
docker compose up -d --build
```

起站後開瀏覽器進 `PUBLIC_BASE_URL`,系統會帶你走一次首次啟動精靈。第一步是組織名稱,第二步就是建立管理員帳號,密碼是你當場輸入的,不會出現在任何 log 或環境變數裡。

建表、寫入資料庫裡的署名紀錄,以及「有設 `SEED_ADMIN_PASSWORD` 才建管理員」這三件事都在後端容器啟動時做完,不需要人工介入,也沒有另外的一次性容器。

兩種建管理員的方式擇一:

- **首次啟動精靈(預設,建議)**:`.env` 不要填 `SEED_ADMIN_PASSWORD`。資料庫裡沒有任何使用者時,`/setup` 才會顯示表單,填完送出就完成。
- **環境變數(自動化部署用)**:`.env` 同時填 `SEED_ADMIN_EMAIL` 與 `SEED_ADMIN_PASSWORD`(至少 12 個字元)。起站後那組帳號就存在,而且標記為「下次登入必須改密碼」。跑完建議把 `SEED_ADMIN_PASSWORD` 從 `.env` 刪掉,它已經沒有 runtime 用途。

資料庫裡一旦有任何使用者,`/setup` 就會顯示「系統已安裝,請登入」,不會再讓人填一遍。這個判斷在進入頁面時就做,不是等到送出才擋。

Docker 與 Zeabur 兩條路線跑的是同一份啟動程式碼(`apps/backend/src/main.ts`,呼叫 `setup/seed-admin.ts` 與 `setup/seed-attribution.ts`),結果一致。舊版的 compose 另外起一個 `bootstrap` 容器做這件事,但那個容器在零設定安裝時必定失敗(它共用後端的環境變數,卻拿不到後端自動產生的 JWT 金鑰),已經移除。

確認狀態:

```bash
docker compose ps
curl -fsS http://localhost:8080/healthz
curl -fsS http://localhost:8080/readyz
```

`/healthz` 回應代表後端活著(liveness),`/readyz` 代表資料庫也通了(readiness)。

`/readyz` 是給 readiness probe 用的,判斷依據是狀態碼:資料庫連得上回 200,連不上回 503
(body 一併帶 `{"status":"degraded","db":"down"}` 方便人看)。Kubernetes 的 `readinessProbe`、
或負載平衡器的健康檢查可以直接接,不需要去 parse body。

**要「DB 不通就別再送流量進來」,得自己把它接上。** 出廠的容器 HEALTHCHECK
(Dockerfile 與 `docker-compose.yml`)刻意打的是 `/healthz` 而不是 `/readyz`:單機
compose 沒有流量輪替可言,而且用 `/readyz` 當容器健康檢查的話,資料庫一抖動容器就會
被判 unhealthy、依 restart 政策進重啟迴圈,反而更難查(後端本來就設計成 DB 連不上
不 crash、等它恢復自己接上)。所以「把這台移出後端池」這件事要由前面的編排器負責:

- **Kubernetes**:把 backend 的 `readinessProbe` 指到 `/readyz`(`livenessProbe` 才用
  `/healthz`)。DB 掛掉時這個 Pod 會被標成 not ready,Service 自動不再把流量送給它,
  DB 恢復後又自動加回來。
- **前置負載平衡器 / 反向代理**:把它的健康檢查路徑設成 `/readyz`(而不是 `/healthz`),
  依 503 把這台移出上游池。
- **單機 compose**:沒有第二台可以輪替,維持 `/healthz` 即可;要監控 DB 狀態就另外
  對 `/readyz` 拉警報。

### 前面已經有公司的負載平衡器或 WAF

把 `SITE_ADDRESS` 留 `:80`,TLS 交給前面那一層處理,並依實際層數調整 `TRUST_PROXY_HOPS`。這個值決定速率限制認到的來源 IP:設太小,所有請求會被算成同一個 IP,一個人就能讓全站吃 429;設太大,`X-Forwarded-For` 可被偽造,速率限制形同虛設。照本 compose 部署且前面沒有別的代理時就是 1,每多一層加 1。

## 三、路線 B:接公司既有的 PostgreSQL

已經有在維運的資料庫就走這條,compose 只起後端、前端、反向代理。

在 `.env` 設整串連線字串:

```
DATABASE_URL=postgresql://帳號:密碼@資料庫主機:5432/資料庫?schema=public
```

之後每次 compose 指令都要多帶一份疊加檔:

```bash
docker compose -f docker-compose.yml -f docker-compose.external-db.yml up -d --build
```

設了 `DATABASE_URL` 之後,`POSTGRES_*` 那幾個變數就不會被用到。資料庫帳號需要在該資料庫上建表與改結構的權限,因為啟動時會自動套用結構變更。

## 四、路線 C:不用 Docker

```bash
pnpm install
cp apps/backend/.env.example apps/backend/.env
cp apps/frontend/.env.example apps/frontend/.env
# 填入 DATABASE_URL、JWT_ACCESS_SECRET
pnpm --filter @mitchcrm/backend exec prisma db push
pnpm --filter @mitchcrm/backend run seed:admin
pnpm build
```

然後用 systemd 或 pm2 之類的方式,分別讓後端與前端常駐:

- 後端:`node apps/backend/dist/main.js`,監聽 `PORT`(預設 8787)
- 前端:`pnpm --filter @mitchcrm/frontend start`,監聽 3000

反向代理的分流規則:`/api/*`、`/healthz`、`/readyz` 轉給後端,其餘全部轉給前端。nginx 的寫法:

```nginx
server {
    listen 443 ssl;
    server_name crm.example.com;

    client_max_body_size 20m;

    location ~ ^/(api|healthz|readyz) {
        proxy_pass http://127.0.0.1:8787;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

`client_max_body_size` 要放得夠大,不然上傳照片會失敗,而且錯誤訊息出現在代理層,後端 log 裡什麼都看不到。

## 五、路線 D:PaaS 一鍵部署

以 Zeabur 為例,其他平台流程類似:

1. fork 這個 repo
2. 建立專案,先加 PostgreSQL 服務
3. 加入兩個服務指向同一個 repo,分別是後端與前端。repo 內附的 `zbpack.*.json` 會告訴平台走 Dockerfile 建置
4. 環境變數:

   後端至少要填 `DATABASE_URL`、`PORT`、**`CORS_ORIGIN`**。`CORS_ORIGIN` 常被漏掉,它同時是 CSRF 的來源白名單,填的必須是**前端**的對外網址;沒填或填錯的話,連登入這種 POST 都會被擋成 403,而且後端不會有明顯的錯誤 log。`JWT_ACCESS_SECRET` 留空時由容器啟動腳本自動產生並寫進掛在 `/var/lib/mitchcrm/secrets` 的 volume;平台把那顆 volume 掛成 root 所有、容器又以非 root 執行時,腳本寫不進去會 exit 1 造成無限重啟,遇到就直接把 `JWT_ACCESS_SECRET` 填成一組至少 32 字元的值(`openssl rand -base64 48`),自動產生那段就整段跳過了。`SEED_ADMIN_EMAIL` 與 `SEED_ADMIN_PASSWORD` 選填,要跳過首次啟動精靈就兩個都填,只填一個不會建帳號。

   前端填 `NEXT_PUBLIC_API_BASE_URL`(後端的對外網址)與 `NEXT_PUBLIC_SITE_URL`(前端自己的網址)。**這兩個是建置時編進 bundle 的,不是啟動時讀的**,平台要把它們當成 docker build 的 build-arg 傳進去才有效(兩份 Dockerfile 都宣告了對應的 `ARG`)。改了值一定要重新建置,只重啟不會生效;沒生效的症狀是畫面打得開、所有 API 都打到 `http://localhost:8080`,瀏覽器主控台一片連線失敗而伺服器端 log 什麼都沒有。

5. 綁定網域,兩個服務用同一個網域配路徑分流,或前端一個網域、後端一個子網域都可以。

   前後端落在**可註冊網域不同**的兩個網域時(例如前端綁自己的網域、後端還留在平台配發的網域),瀏覽器會把登入請求視為跨站,`SameSite=lax` 的登入 cookie 根本不會送出去。症狀是登入回應 200、下一個請求就變成未登入,伺服器端完全正常。那種佈局要把後端的 `COOKIE_SAMESITE` 設成 `none` 並且 `COOKIE_SECURE=true`。代價是少掉一道 CSRF 防線(剩後端的 Origin 檢查),所以能用同一個可註冊網域就盡量用。

有一件事在每個平台都要對齊:反向代理轉發的目標埠、容器對外宣告的埠、`PORT` 環境變數,三者必須一致。任一個不齊就是 502。有些平台還多一層「內網存取埠」與「公開網路埠」,也要一起對齊。

## 六、備份與還原

### 要備份四樣東西

1. 資料庫
2. `.env` 裡的金鑰
3. 照片。照片就在資料庫裡,備份資料庫等於備份照片
4. **`app-secrets` volume 裡自動產生的金鑰**,見下一段

金鑰跟資料庫備份請分開存放。

#### 沒有在 `.env` 指定金鑰的話,金鑰只存在 volume 裡

`.env` 的 `JWT_ACCESS_SECRET` 留空時,容器啟動腳本會自己產生一把(只有這一把),
寫進 `app-secrets` 這個 Docker volume(容器內路徑 `/var/lib/mitchcrm/secrets`)。
這是 README 主推的裝法,也就是說**多數人的金鑰唯一副本在那個 volume 裡,不在 `.env` 裡**。
只備份資料庫跟 `.env` 會漏掉它。volume 一沒,權杖就驗不過,全體使用者的登入狀態同時失效,
必須每個人重新登入。

把 volume 裡的金鑰抄出來:

```bash
docker compose exec backend sh -c 'cat /var/lib/mitchcrm/secrets/*'
```

抄出來之後有兩種做法,擇一:

- **寫回 `.env`(建議)**:把值填進 `.env` 的 `JWT_ACCESS_SECRET`,
  再 `docker compose up -d`。之後金鑰以 `.env` 為準,備份 `.env` 就夠,不必再管那個 volume。
  這也讓「換一台機器重建」變成把 `.env` 跟資料庫 dump 搬過去就好
- **繼續讓容器管**:那就要把 volume 一起納入備份排程,跟金鑰同等級保護

金鑰檔的內容等同密碼,抄出來之後不要留在終端機記錄或共用目錄裡。

**備份請比照正式資料保護。** 系統不做欄位層加密,資料庫裡的客戶姓名、電話、地址、
到訪座標與照片都是明文,`pg_dump` 出來的檔案內容跟正式資料一模一樣。丟到公用雲端硬碟、
沒有加密的外接碟或任何共用目錄,等於把整份客戶資料交出去。備份檔要加密、要限制存取、
要有保存期限,銷毀時也要確實刪除。詳見 [`SECURITY.md`](../SECURITY.md)。

### 備份

**先決定備份檔要放在哪裡,而且不要放在 repo 目錄底下。** 下面的指令都是把 dump 寫到當下的
工作目錄,而照 README 的安裝流程走的話,那個目錄就是 clone 下來的 `mitch-crm/`。
dump 的內容跟正式資料一模一樣,一旦事後在同一份 clone 上改東西送 PR,整份客戶資料就跟著
push 上公開 repo。`.gitignore` 已經擋掉 `*.dump`、`*.sql`、`*.tar` 這幾類副檔名當作最後一道
保險,但別靠它:換個檔名就繞過去了。請先建一個 repo 以外的備份目錄再下指令,例如:

```bash
mkdir -p ~/mitchcrm-backups && cd ~/mitchcrm-backups
```

下面的指令都假設你人已經在那個目錄裡(compose 指令加 `-f /path/to/mitch-crm/docker-compose.yml`,
或先 `export COMPOSE_FILE=/path/to/mitch-crm/docker-compose.yml`)。

用 compose 內建資料庫:

```bash
docker compose exec -T postgres pg_dump -U mitchcrm -Fc mitchcrm > backup-$(date +%F).dump
```

外部資料庫:

```bash
pg_dump "$DATABASE_URL" -Fc > backup-$(date +%F).dump
```

排程建議每天一次,保留 30 份,另外每月一份異地保存。

### 還原

```bash
docker compose stop backend frontend
docker compose exec -T postgres pg_restore -U mitchcrm -d mitchcrm --clean --if-exists < ~/mitchcrm-backups/backup-2026-09-01.dump
docker compose start backend frontend
```

### 演練

備份沒有還原過就不算備份。建議每季在測試機還原一次,並登入確認資料與照片都讀得到。演練用的測試機同樣要當成正式環境保護,結束後把還原的資料庫刪乾淨。

## 七、升級與回滾

### 0.1.0 沒有可以回滾的上一版

0.1.0 是第一個公開版本,也是這個 repo 上的第一個 tag。它之前沒有公開發布過任何版本,所以現在沒有「上一個 tag」可以切回去,也沒有需要反轉的結構變更。第一次部署就照上面的路線裝起來即可,這一節從下一版開始才用得到。

### 升級

資料庫結構變更設計成純新增,服務啟動時自動套用,可重複執行不會損壞既有資料,所以升級不需要人工進資料庫下 SQL。

```bash
cd mitch-crm
docker compose exec -T postgres pg_dump -U mitchcrm -Fc mitchcrm > ~/mitchcrm-backups/pre-upgrade.dump   # 先備份,寫到 repo 以外的目錄
git pull
docker compose up -d --build
docker compose logs -f backend
```

升級前請先讀 [`CHANGELOG.md`](../CHANGELOG.md)。純新增是「升級方向」的保證,不是「回滾方向」的保證,所以哪一版含有不是純新增的變更、回滾前要先做什麼,一律寫在 CHANGELOG 該版本的條目裡。沒有標註就表示那一版不需要人工處理。

### 回滾

**升級前的 dump 是回滾的依據,不是形式。** 升級之前一定要先做,而且要確認檔案真的有內容(`ls -l` 看大小,不要只看指令沒報錯)。

結構是純新增的版本之間,回滾就是切回上一個 tag 再重新建置:舊版程式會忽略它不認得的新欄位,資料庫不必動。

```bash
git checkout <要回到的版本 tag>
docker compose up -d --build
docker compose logs -f backend
```

CHANGELOG 標註了「回滾需要人工處理」的版本,光切 tag 不夠,資料庫也要回到舊版的形狀。做法是用升級前的 dump 還原:

```bash
git checkout <要回到的版本 tag>
docker compose stop backend frontend
docker compose exec -T postgres pg_restore -U mitchcrm -d mitchcrm --clean --if-exists < ~/mitchcrm-backups/pre-upgrade.dump
docker compose up -d --build
```

代價很直接:**升級之後到還原之間新增的資料會一起消失**。沒有升級前的 dump、又不能丟資料的話,就只能自己連進資料庫、依 CHANGELOG 寫的內容把那一版的結構變更逐一反轉,這條路請務必先在測試機上完整走一次再動正式環境。

### 驗證

回滾或升級之後都做同一組確認,不要只看容器有沒有起來:

```bash
docker compose ps
curl -fsS http://localhost:8080/healthz
curl -fsS http://localhost:8080/readyz
docker compose logs --tail=100 backend
```

接著用瀏覽器登入一次,打開客戶清單與拜訪地圖,確認資料與照片都讀得到。任何情況下,動手之前都先做一次現況備份,不要拿正式環境當第一次嘗試。

## 八、常見問題

### 502 Bad Gateway

三個埠沒對齊是最常見的原因:反向代理轉發的目標埠、容器對外宣告的埠、`BACKEND_PORT`(或 `PORT`)。三者要一致。

檢查順序:

```bash
docker compose ps                  # 後端容器是不是 running
docker compose logs backend        # 有沒有啟動失敗的錯誤
docker compose exec caddy sh -c 'wget -qO- "http://backend:${BACKEND_PORT:-8787}/healthz"'
```

最後那一行刻意讀容器裡的 `BACKEND_PORT`,不寫死 8787:埠沒對齊正是這一節在查的問題,診斷指令自己寫死一個埠的話,只會多一個連不上的結果。

如果後端容器一直重啟,通常是環境變數缺了必填項,log 第一行會寫是哪一個。

還有一種情況是後端還在啟動、代理已經開始轉發。第一次建置後給它 30 秒左右再測。

### 資料庫連不上

依序確認:

```bash
docker compose logs postgres | tail -30
docker compose exec backend node -e "console.log(process.env.DATABASE_URL)"
```

常見原因:

- **第一次啟動之後才改 `POSTGRES_PASSWORD`。** 這是最常見的一種:postgres 官方映像只在資料目錄還是空的時候拿那個值建帳號密碼,之後每次啟動都只是掛上既有的 `postgres-data` volume。所以先零設定 `docker compose up -d` 跑起來、之後才跑 `scripts/setup.sh` 或手動填密碼的話,`.env` 是新密碼、資料庫裡還是舊密碼,log 會出現 `password authentication failed for user "mitchcrm"`,`/readyz` 回 503,畫面打得開但每一支 API 都失敗。修法兩條擇一:

  ```bash
  # (a) 進資料庫把密碼改成 .env 裡的那一組
  docker compose exec postgres psql -U mitchcrm -d mitchcrm \
    -c "ALTER USER mitchcrm WITH PASSWORD '這裡填 .env 裡的新密碼';"
  docker compose up -d

  # (b) 資料還可以丟的話整組重來(會刪光資料庫內容,想清楚再做)
  docker compose down -v
  ```

- 密碼含 `@` `:` `/` `?` `#` 這些字元,被組進連線字串時沒做 URL 編碼。改成只用英數字最省事
- 接外部資料庫但忘了帶疊加檔,compose 還是起了自己那台
- 外部資料庫的 `pg_hba.conf` 沒放行來源 IP,或防火牆擋住 5432
- 資料庫帳號沒有建表權限,現象是啟動時卡在套用結構變更那一步

### 地理編碼失敗

現象是新增客戶後,拜訪地圖上看不到那一家。

- 用公用 Nominatim 而沒填聯絡信箱:對方會擋掉沒有識別資訊的請求。到後台系統設定的「地圖與地理編碼」頁籤補上信箱,或在環境變數設 `NOMINATIM_EMAIL`(後台那一格留空時會退回讀這個變數)
- 打太快被限流:公用服務有每秒一次的限制,大量匯入名單時一次補不完。每次打開拜訪地圖都會再補一批,多開幾次就補齊了
- 地址本身查不到:門牌不完整、只有大樓名稱、地址寫在備註裡,這幾種都查不到。到客戶卡把地址補完整,下次打開地圖就會重新編碼
- 內網封閉環境:沒有對外連線就無法地理編碼。可以自架一份 Nominatim,在後台的「地圖與地理編碼」頁籤把服務位址指過去

要確認是不是服務端的問題,看後端 log 裡的地理編碼記錄,它會寫失敗原因的類型。

### 登入成功卻馬上被踢回登入頁

`COOKIE_SECURE` 設成 `true` 但實際走的是 http,瀏覽器會直接丟掉 cookie。純 http 試跑要設 `false`。

### 上傳照片失敗

反向代理的請求大小上限太小。內建的 Caddy 設定沒有這個限制,自己接 nginx 的話要調 `client_max_body_size`。

### 全站一直回 429

`TRUST_PROXY_HOPS` 設太小,所有人被算成同一個來源 IP。照實際的代理層數調整。

## 十、資料如何取出 / 換系統

導入會議上一定會被問的那一題:「三年後我要換掉你,資料怎麼帶走。」
兩條路,依你要帶走多少而定。

### 路一:後台匯出(不需要工程師)

後台「客戶管理」底下的「資料管理」有三支匯出,直接下載 CSV:

| 匯出 | 內容 | 對應資料表 |
|---|---|---|
| 客戶清單 | 客戶主檔,前十欄與匯入格式相同 | `dev_customers` |
| 互動紀錄 | 每一筆互動、打卡與系統紀錄 | `dev_interactions` |
| 存證照片清單 | 每張照片的中繼資料與下載路徑,不含照片本體 | `dev_visit_photos` |

編碼是 UTF-8 帶 BOM,Excel 直接打得開不會亂碼;換行是 CRLF;
`Content-Disposition` 是 `attachment`,檔名長這樣:`customers-20260905-1430.csv`。

一次上限 5000 筆(照片清單 10000 筆)。要更多就分批:

```bash
# 用瀏覽器登入後複製 cookie,或用你自己的自動化流程帶上驗證
curl -b cookies.txt -OJ "https://crm.example.com/api/admin/crm-export/customers?offset=0"
curl -b cookies.txt -OJ "https://crm.example.com/api/admin/crm-export/customers?offset=5000"
```

回應標頭 `X-Export-Truncated: true` 表示還有下一批,`X-Export-Next-Offset` 就是下一批的起點。
匯出範圍依登入者的可見範圍而定,系統管理員拿得到全部。每一次匯出都會寫進 `audit_logs`。

**存證照片本體**逐張走 `GET /api/admin/crm-checkin/photo/<照片編號>`,
照片編號在照片清單的「照片編號」那一欄,清單另外附 SHA-256 可以驗證檔案沒有被改過。
幾百張這樣抓沒問題,幾萬張請改走路二。

### 路二:`pg_dump`(整套帶走,含照片)

照片存在資料庫的 `dev_visit_photos.bytes` 欄位裡(PostgreSQL 的 `bytea`),
一個組織跑一年大約是幾 GB,不適合從網頁一次拉走。整套搬移就是一份 dump:

```bash
mkdir -p ~/mitchcrm-export && cd ~/mitchcrm-export
docker compose exec -T postgres pg_dump -U mitchcrm -Fc mitchcrm > mitchcrm-$(date +%F).dump
```

外部資料庫:

```bash
pg_dump "$DATABASE_URL" -Fc > mitchcrm-$(date +%F).dump
```

這份檔案就是全部,沒有任何資料存在資料庫以外的地方(除了 `.env` 裡的金鑰,見第六節)。
要餵給別的系統的話,`-Fp --inserts` 會產出可讀的 SQL,或者用 `psql \copy` 把單張表倒成 CSV:

```bash
docker compose exec -T postgres psql -U mitchcrm -d mitchcrm \
  -c "\copy (SELECT id, company_name, tax_id, stage, contact_name, contact_phone, actual_address FROM dev_customers WHERE deleted_at IS NULL) TO STDOUT WITH CSV HEADER" \
  > customers.csv
```

把照片倒成一個一個檔案(注意這會產生大量小檔,先確認硬碟空間):

```bash
docker compose exec -T postgres psql -U mitchcrm -d mitchcrm -At \
  -c "SELECT id, encode(bytes,'base64') FROM dev_visit_photos" \
  | while IFS='|' read -r id b64; do echo "$b64" | base64 -d > "photo-$id.jpg"; done
```

**資料表對照**(要自己寫轉檔程式時用得到):

| 資料表 | 內容 |
|---|---|
| `dev_customers` | 客戶主檔。`deleted_at` 不為 null 就是已刪除(回收桶裡的) |
| `dev_interactions` | 互動、備註與打卡。`note` 以「【」開頭的是系統自動寫的 |
| `dev_visit_photos` | 存證照片,`bytes` 是照片本體 |
| `dev_visit_plans` | 拜訪排程 |
| `dev_daily_reports` | 日報 |
| `dev_stages` / `dev_categories` / `dev_premises_types` / `dev_interaction_channels` / `visit_photo_kinds` | 後台可改的主檔,客戶身上存的是它們的 `key` |
| `users` / `departments` | 帳號與組織 |
| `audit_logs` / `error_logs` | 稽核與錯誤記錄 |
| `system_settings` | 後台設定,一列一種(見 schema 註解) |

**dump 出來的檔案跟正式資料一模一樣。** 加密、限制存取、用完刪掉,做法同第六節的備份。

## 十一、維運節奏:多久要做什麼,需不需要工程師

### 節奏表

| 頻率 | 要做的事 | 需要工程師嗎 |
|---|---|---|
| 每天(自動) | 資料庫備份 | 排程設好之後不用 |
| 每週 | 看一次後台的錯誤記錄頁,有沒有一直重複的同一種錯 | 不用。看得懂就處理,看不懂就把那一列截圖丟給工程師 |
| 每週 | 回收桶看一眼,確認沒有誤刪放著沒人還原 | 不用 |
| 每月 | 檢查磁碟用量,尤其是照片(見下面) | 不用看,滿了才要 |
| 每月 | `docker compose pull && docker compose up -d --build` 更新到最新版 | 不用,但升級後要有人登入確認 |
| 每季 | 備份還原演練(見第六節) | 建議要 |
| 每季 | 使用者清單盤點:離職的帳號停用了嗎、名下客戶轉出去了嗎 | 不用 |
| 出事當下 | 看 `docker compose logs -f backend` | 要 |

### 這幾件事目前一定要工程師直連資料庫

講清楚比較好,免得導入之後才發現卡住:

1. **大量清理存證照片。** 系統只有「單張刪除」與「永久刪除整個客戶」,
   沒有「刪掉兩年前的所有照片」這種批次操作。空間吃緊時要下 SQL,例如
   `DELETE FROM dev_visit_photos WHERE taken_at < now() - interval '2 years'`。
   下之前一定要先備份,而且要清楚這些照片是不是還在舉證期間內
2. **批次修資料。** 「把所有電話的區碼補上 0」這種。
   有一條不必連資料庫的路:匯出客戶 CSV、在 Excel 改、再匯入(見第十節與功能說明 3.19),
   但匯入是新增不是更新,已經存在的那幾筆會被略過。要「改既有的」還是得下 SQL
3. **改資料表結構、加索引、調整 PostgreSQL 參數**
4. **看資料庫層的稽核記錄。** `audit_logs` 目前沒有後台查詢畫面

其餘的日常事務(新增使用者、改設定、改階段、改照片檢查表、刪客戶、還原、匯出)
都在後台點得到,不需要工程師。
